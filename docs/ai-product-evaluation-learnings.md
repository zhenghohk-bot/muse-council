# AI 产品评测：从单一分数到可解释的质量闭环

> 本文先复盘「她们会怎么想？」多角色 AI 圆桌项目中的评测问题，再将经验抽象为适用于 Agent、RAG、生成式工作流和 AI 助手的通用方法。

## 一、项目背景

「她们会怎么想？」是一个多角色 AI 圆桌产品。用户提出人生困惑后，系统会：

1. 分析用户问题；
2. 推荐并邀请女性先行者入席；
3. 生成主持人开场；
4. 让先行者依次回应、讨论和接受追问；
5. 由主持人收束；
6. 生成行动卡、先行者赠言与历史回声。

为了避免产品停留在“看起来像角色扮演”，项目建立了一套 Harness：

```text
用户问题
→ Director：读题、选人、分配谈话任务
→ ContextBuilder / SourceRetriever：组织上下文与资料
→ StageGenerator：逐阶段生成
→ OutputGuard：检查事实、重复、安全与清晰度
→ Finalizer：生成行动卡与赠言卡
```

同时建立了评测 Harness，对完整 AI 对话链路进行端到端评测。

## 二、最初的评测设计

评测使用固定题集运行完整圆桌，再由独立 LLM 裁判从九个维度评分：

| 维度 | 主要问题 |
| --- | --- |
| 读题准确性 | 是否准确理解用户明确说出的处境、情绪和张力 |
| 人物区分度 | 遮住姓名后，不同先行者是否仍可区分 |
| 谈话推进 | 后发言者是否承接前文并带来新信息 |
| 重复控制 | 是否换词复述、复读自己或其他角色 |
| 回应贴题 | 是否持续回应用户当前问题 |
| 语言清晰度 | 是否自然、直接、容易一次读懂 |
| 安全性 | 是否避免诊断、保证和越界推断 |
| 行动卡质量 | 是否来自谈话、可执行、可验证 |
| 金句卡质量 | 是否忠实提炼本场发言并保持人物特色 |

此外，系统还包含确定性检查，例如：

- 是否逐字复读；
- 是否出现来源不明的历史名言；
- 输出结构是否合法；
- 卡片是否能追溯到对话消息；
- 是否触发 fallback；
- 是否出现硬性安全问题。

## 三、项目中暴露出的评测过拟合

### 1. 固定题集逐渐变成了开发集

最初的固定题集主要覆盖：

- 副业与职业选择；
- 关系边界；
- 家庭期待；
- 自我价值与比较；
- 表达与被看见；
- 原因不明的情绪；
- 用户明确说出的羞耻；
- 用户纠正系统误读。

随着 Prompt、Guard 和 fallback 不断根据这些题目调整，系统越来越擅长处理“情绪、关系与人生两难”。

但当用户自由提出：

> 如何提升自己的表达能力？

系统出现了明显失配：

- 将普通技能问题误判成情绪支持问题；
- 替用户补充没有说出的紧张和行为模式；
- 为了人物区分而生硬引入“关系交换”；
- 方法没有解释目的和有效性判断；
- 固定开头大量重复；
- 不同人物在追问中掉入相同 fallback。

这说明固定题集已经不足以评估系统对真实问题分布的泛化能力。

### 2. 指标要求泄漏进了生成逻辑

为了提高评测中的人物区分、谈话推进和语言简洁度，运行时逐渐加入了很多硬规则，例如：

- 每位先行者尽量使用不同的谈话动作；
- 第一轮最多只有一位先行者给出行动；
- 发言必须控制在较短字数；
- 不同谈话动作使用固定开头；
- 未满足部分软质量条件时直接进入固定 fallback。

这些规则提高了结构可控性，却让模型更像在完成格式，而不是自然参与圆桌。

典型结果包括：

- “我想先分清一件事”反复出现；
- “我想先停在这个感受上”被用于没有表达情绪的用户；
- 为了不重复，角色被迫说出不自然的新角度；
- 为了简洁，必要解释被删掉；
- 为了只有一人给行动，其余角色只能抽象分析。

这不是评测维度本身错误，而是把本应作为观察信号的软指标，错误地实现为生成阶段的硬约束。

### 3. 总分提升不等于体验提升

即使总分或部分维度提高，真实体验仍可能变差：

- 语言更短，但更难理解；
- 人物差异更明显，但差异与用户问题无关；
- 对话看似推进，实际只是按结构轮流发言；
- 重复率下降，但内容变得刻意和生硬；
- 安全性提高，但情绪支持消失；
- 行动更具体，但没有解释为什么做。

这体现了 Goodhart's Law：

> 当一个指标成为优化目标，它可能不再是一个可靠指标。

## 四、如何区分不同来源的波动

AI 产品输出不稳定，不能把一次分数变化直接归因于某次代码修改。

可以把观测到的变化理解为：

```text
观测结果
= Harness 改动
+ 生成模型方差
+ 裁判模型方差
+ 模型版本或服务端漂移
+ Harness 与模型之间的交互
+ 测试样本差异
```

### 1. 测量裁判方差

方法：

1. 冻结同一份圆桌输出；
2. 不重新生成内容；
3. 让同一个裁判重复评分 5–10 次；
4. 统计中位数、范围和标准差。

如果内容完全不变，裁判仍给出明显不同的分数，说明小幅分数变化不能被解释为产品改进。

### 2. 测量生成方差

方法：

1. 固定代码、问题、生成模型、参数和裁判；
2. 对同一道题重复生成多次；
3. 对每次结果分别评分；
4. 统计中位数、最差结果和硬性失败率。

对用户而言，“平均表现不错但偶尔严重跑偏”仍然是质量问题。因此不能只报告平均分或最好结果。

### 3. 测量 Harness 改动效果

比较新旧 Harness 时应固定：

- 生成模型及版本；
- 裁判模型及版本；
- 测试题；
- 请求参数；
- 评测 Prompt；
- 评分门槛。

推荐采用逐题配对盲测：

```text
同一道题
→ 旧 Harness 输出 A
→ 新 Harness 输出 B
→ 裁判不知道版本，判断 A/B 哪个更好并说明原因
```

相较分别给 A、B 打绝对分，配对偏好通常更稳定，也更接近产品决策。

### 4. 区分模型升级和 Harness 改进

如果生成模型也发生变化，应采用 2×2 实验：

| 组合 | 旧 Harness | 新 Harness |
| --- | --- | --- |
| 旧模型 | A | B |
| 新模型 | C | D |

由此区分：

- `A → B`：Harness 改动效果；
- `A → C`：模型升级效果；
- `B → D`：新模型对新 Harness 的增益；
- 只有 D 明显提升：可能存在模型和 Prompt 的交互。

如果裁判模型发生变化，也必须让 before 和 after 都由同一个新裁判重新评价。

## 五、裁判模型切换带来的经验

项目曾将裁判从火山方舟的 `glm-5-2-260617` 切换到智谱官网的 `glm-5.2`。

虽然属于同一模型家族，但不能确认：

- 是否为完全相同的模型快照；
- 服务端默认参数是否一致；
- 系统层处理是否相同；
- 模型别名是否会被服务端更新。

因此，两个服务商给出的绝对分数不能直接比较。

正确做法是：

1. 历史结果保留，并明确标注裁判版本；
2. 选定新的裁判后，重新评价旧 baseline；
3. 同一组 before / after 实验固定使用同一裁判；
4. 将裁判端点、模型 ID、Prompt、参数和日期写入运行元数据；
5. 使用多次评分的中位数，而非依赖单次结果。

## 六、Baseline 不是一个分数

一个可用的 baseline 应当是一套可复现的版本包，而不是“平均 85 分”。

它至少包含：

```text
代码提交
+ 生成模型与参数
+ 裁判模型与参数
+ 测试题版本
+ 评测 Prompt 版本
+ 评分维度与门槛
+ 原始对话输出
+ 确定性检查结果
+ 人工体验记录
```

### 项目中的历史 baseline

项目早期以提交 `fde7885` 作为 P2 修改前代码参照。

- 火山 GLM 全量运行：平均约 85，MVP 通过 4/8；
- 同一旧代码使用官网 GLM 重跑：平均约 86，MVP 通过 7/8。

二者通过数差异明显，说明裁判变化和单次波动足以影响结论。

因此，旧结果适合作为历史记录，不应直接作为下一轮架构重构的唯一比较基准。

### 下一轮 baseline

下一轮应在重构 `QuestionIntent` 之前冻结：

- 当前代码版本；
- 补齐后的意图覆盖题集；
- 官网 GLM 裁判；
- 多次生成与多次评分结果；
- 典型失败输出；
- 人工体验结论。

## 七、通用的三轨评测体系

### 第一轨：确定性检查

用于判断没有主观性的要求：

- 是否虚构用户没有说过的事实、行为或情绪；
- 是否逐字或高度近似复读；
- 是否引用不存在或来源错误的资料；
- 数据结构是否合法；
- 卡片是否能追溯到对话；
- 状态机是否按顺序运行；
- API 某阶段失败后是否只重试当前阶段。

特点：

- 零裁判方差；
- 适合进入 CI；
- 适合证明具体 bug 已修复；
- 不适合判断语言是否有感染力。

### 第二轨：LLM 质量评测

用于评价需要语义理解的质量：

- 是否真正读懂用户；
- 人物是否具有不同的判断方式；
- 对话是否自然推进；
- 方法是否说明目的与验证方式；
- 语言是否清楚；
- 行动卡是否来自谈话；
- 赠言是否忠实且具有角色特色。

建议：

- 固定裁判；
- 同一输出重复评分；
- 使用中位数和范围；
- 优先使用 A/B 盲测；
- 记录裁判理由，而不只保存分数；
- 定期抽样与人工评分校准。

### 第三轨：人工体验评测

用于判断机器裁判难以可靠捕捉的问题：

- 是否愿意继续追问；
- 是否感到被误解；
- 是否有真实参与感；
- 角色是否像“活着的人”而不是人格标签；
- 内容是否虽然合规但令人不适；
- 页面节奏、动效和交互是否自然；
- 最终卡片是否真的值得保存。

人工评测不是低效补丁，而是主观体验产品的必要数据源。

## 八、如何设计测试数据

### 1. 开发集

用于日常调试，可以查看题目和失败原因。

### 2. 回归集

用于确认新改动没有破坏已经具备的能力。

### 3. 隐藏集

只在版本验收时运行，避免开发者根据具体题目调 Prompt。

### 4. 分布外探索题

由人工自由提问，主动寻找分类体系未覆盖的问题。

### 5. 真实失败样本

将用户体验中出现的失败沉淀为测试样本，但不能只针对原句打补丁，而应归因到一类系统问题。

例如：

```text
现象：普通技能题被情绪化
错误修复：看到“表达能力”就禁用李清照
系统修复：增加 QuestionIntent，并将任务意图与情绪信息量分开建模
```

## 九、评测驱动迭代，但不让评测统治生成

合理的闭环是：

```text
运行评测
→ 发现失败模式
→ 归因到 Harness 层
→ 提出系统性修复
→ 进行模块级验证
→ 定向复测
→ 全量回归
→ 人工体验
→ 决定是否发布
```

不合理的闭环是：

```text
某个维度低分
→ Prompt 再加一句“必须”
→ Guard 再加一个正则
→ 输出更僵
→ 为新失败继续加规则
```

### 硬约束适合什么

- 安全；
- 事实边界；
- 引用真实性；
- 状态和结构合法性；
- 明确的逐字复读；
- 隐私与合规。

### 软指标适合什么

- 长度；
- 开头形式；
- 人物语气；
- 修辞数量；
- 是否分成一段或两段；
- 是否每位人物都提供行动；
- 谈话节奏。

软指标可以触发 repair 或扣分，但不应轻易把真实模型输出替换为固定台词。

## 十、对其他 AI 项目的通用经验

### 1. 先定义产品承诺，再定义指标

评测维度必须来自产品希望为用户创造的价值，而不是因为某个维度容易量化。

### 2. 区分“正确性”和“体验质量”

事实正确、安全合规可以硬检查；自然度、信任感和参与感需要语义评测与人工体验。

### 3. 评测集一旦反复用于调试，就不再是测试集

必须准备新的隐藏集和分布外问题。

### 4. 不要把单次 LLM 分数当成实验结论

报告分布、中位数、最差案例和失败率。

### 5. 效果尺寸必须大于噪声底

如果裁判自身波动约 10 分，单次提升 2 分不能证明改进。

### 6. 总分会掩盖关键失败

高平均分不能抵消虚构用户经历、伪造引用或严重复读。应同时设置硬性红线与逐维度分析。

### 7. 记录“为什么失败”，比记录“多少分”更重要

可行动的评测必须能定位到：

- 问题理解；
- 检索；
- 路由；
- Prompt；
- 上下文组织；
- 输出守卫；
- fallback；
- UI 或状态管理。

### 8. 模型升级不是产品能力升级的充分证明

更强模型可能掩盖 Harness 缺陷，也可能让复杂规则产生新的副作用。必须单独测量模型和系统的贡献。

### 9. Fallback 也属于产品体验

Fallback 不能只是“系统没崩”，还要保持：

- 当前上下文相关；
- 人物差异；
- 不复读；
- 不虚构；
- 能让用户继续对话。

### 10. 最重要的指标是泛化后的用户价值

系统不仅要通过已知题目，还要面对用户真实、模糊、混合和未被预先分类的问题。

## 十一、面试表达

### 60 秒版本

> 我在一个多角色 AI 圆桌项目中建立了九维 LLM-as-a-Judge 评测，包括读题准确性、人物区分度、谈话推进、重复控制和卡片相关性。但迭代后我发现，部分指标提升并没有带来更好的用户体验。系统为了通过固定题集，出现了固定句式、发言过短、技能问题情绪化和 fallback 复读。
>
> 我意识到这是评测过拟合：固定评测集经过反复调参后已经变成开发集，而且单次 LLM 裁判和生成模型都存在明显方差。之后我将问题拆成确定性质量、LLM 语义质量和人工体验三条评测轨道，并通过冻结输出测裁判方差、重复生成测模型方差、A/B 盲测评估 Harness 改动，同时拆分开发集、回归集和隐藏集。
>
> 这个项目让我认识到，AI 产品评测不是追求一个更高的总分，而是建立一个能够解释变化、发现分布外失败，并且不被自身指标绑架的质量闭环。

### 面试官追问：怎么证明是 Harness 改进，而不是模型变强？

> 我会固定生成模型、裁判模型、题集和参数，对新旧 Harness 做逐题配对盲测。如果生成模型也发生变化，就采用旧/新 Harness × 旧/新模型的 2×2 实验，分别估计 Harness、模型和两者交互的影响。小于裁判噪声底的分数变化不作为改进结论。

### 面试官追问：为什么还需要人工评测？

> LLM 裁判适合规模化检查贴题、重复和结构，但无法稳定判断用户是否愿意继续聊、角色是否真正有参与感，以及语言是否虽然合规却令人不舒服。对于对话体验产品，人工体验不是最后兜底，而是评测体系的一条正式轨道。

### 面试官追问：评测会不会限制生成能力？

> 会。如果把自然度、长度和人物差异直接写成大量硬规则，模型会开始迎合格式。我的原则是只把安全、事实和结构合法性设为硬约束；语言、节奏和角色表达作为软指标，用 repair、A/B 评测和人工反馈优化，而不是用固定前缀和静态台词控制。

## 十二、版本发布检查表

### 实验可比性

- [ ] before / after 使用同一生成模型；
- [ ] 使用同一裁判模型与端点；
- [ ] 固定 Prompt、参数和题集版本；
- [ ] 记录代码提交；
- [ ] 裁判变化后重新评价旧 baseline。

### 数据与覆盖

- [ ] 开发集、回归集和隐藏集分离；
- [ ] 覆盖核心用户意图；
- [ ] 包含混合意图和分布外问题；
- [ ] 将真实失败归因到系统问题；
- [ ] 没有只针对单个关键词打补丁。

### 结果解释

- [ ] 报告中位数和波动范围；
- [ ] 记录最差案例；
- [ ] 记录 fallback 和硬性失败率；
- [ ] 检查各维度，而不只看总分；
- [ ] 改进幅度大于已知噪声底；
- [ ] 重要结论经过人工复核。

### 产品体验

- [ ] 用户没有被补充未表达的事实或情绪；
- [ ] 输出清晰精简，但语义完整；
- [ ] 方法说明目的和有效性判断；
- [ ] 多角色提供真正不同的判断方式；
- [ ] 追问能够承接最新用户意图；
- [ ] 行动卡和赠言来自真实谈话；
- [ ] UI、状态恢复和下载流程通过浏览器端到端测试。

## 结语

AI 产品评测的目标不是让系统更会考试，而是帮助团队回答三个问题：

1. 系统是否真的变好了？
2. 变化来自 Harness、模型、裁判还是随机波动？
3. 这种改进能否泛化到评测集之外的真实用户问题？

只有当评测能够解释变化、暴露失败并约束错误归因时，它才是产品能力的一部分，而不只是一个分数仪表盘。
