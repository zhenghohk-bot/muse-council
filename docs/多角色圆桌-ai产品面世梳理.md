## 0. 使用方式

- 先熟悉“30 秒版”和“2 分钟版”，不要逐字背诵。
- 项目题优先使用“用户问题 → 产品判断 → 技术方案 → 评测证据 → 反思”结构。
- 技术题不需要假装自己是算法工程师，但要能解释关键模块、取舍、风险和验证方法。
- 数据只引用已经真实运行或记录过的结果，不把尚未完成的迭代描述为已上线成果。
- 面试重点不是证明产品已经完美，而是证明自己能发现 AI 系统问题、定位根因并建立可迭代的产品机制。

## 2. 自我介绍中的项目讲法

### 2.1 30 秒版

我最近独立做了一个多角色 AI 圆桌产品。用户输入一个人生问题，系统会分析意图、推荐三位女性先行者，再通过分阶段对话形成行动卡和有来源的赠言卡。这个项目对我最大的价值不是做了一个聊天界面，而是把不稳定的 LLM 生成拆成了一套 Harness：包括状态机、角色调度、来源检索、结构化输出、Guard、fallback 和评测闭环。我也真实遇到了人物同质化、追问误判、重复兜底和裁判模型波动，最后把这些失败定位到具体系统层，而不是只靠改 Prompt。

### 2.2 2 分钟版

我做这个项目的起点，是发现普通 AI 在面对模糊的人生问题时，往往只给一个单一、泛化的答案，用户缺少参与感，也很难把谈话转成行动。因此我设计了“女性先行者圆桌”：用户先提问，系统推荐三位不同视角的先行者，她们按顺序回应、补充或讨论，用户可以继续追问，最后生成行动卡和赠言卡。

第一版其实只是一次性生成，内容很像报告，人物也不够真实。后来我把核心重构成 Roundtable Harness：Director 负责读题和调度，StageGenerator 分阶段调用模型，SourceRetriever 从人工核验的资料中召回人物依据，OutputGuard 检查事实边界、重复和越界，最终再生成与本场对话绑定的卡片。接口采用 OpenAI 兼容协议，因此生成模型可以切换，API 失败时也只重试当前阶段并有本地降级。

项目里最重要的一次学习来自评测。我最初用独立 LLM 从九个维度评分，但后来发现固定题集会变成开发集，裁判本身也有明显方差，单次分数不能证明改进。因此我把评测改成三轨：确定性检查证明具体 Bug 是否修复，LLM 裁判负责发现整体退化，人工体验判断自然度、参与感和人物区分。这个过程让我认识到，AI 产品经理不仅要设计功能，还要设计模型在什么结构里工作、失败时怎么降级，以及如何判断一次迭代真的变好了。

## 3. 项目全景速记

### 3.1 用户与问题

- 目标用户：希望梳理人生困惑、获得多元女性视角并形成下一步行动的人。
- 用户问题：普通 AI 回答单一、泛化；角色扮演容易只有语气，没有真实判断差异；谈话结束后缺少可执行结果。
- 核心价值：不是让用户模仿名人，而是借不同视角看清问题，再由用户做自己的决定。

### 3.2 核心流程

```text
用户提问
→ 识别 QuestionIntent / SupportMode
→ 推荐并选择 3–5 位先行者
→ 主持人开场
→ 第一轮逐人回应
→ Director 决定递进 / 互补 / 澄清 / 交锋 / 跳过
→ 用户定向追问
→ 主持人收束
→ 行动卡 + 本场赠言 + 可选历史回声
```

### 3.3 核心架构

| 模块 | 作用 | 产品意义 |
| --- | --- | --- |
| `RoundtableDirector` | 读题、选人、分配任务、决定讨论模式和追问者 | 把“谁在什么时候说什么”从模型自由发挥变成可解释调度 |
| `ContextBuilder` | 组装问题、历史、人物、显式情绪和否定假设 | 控制上下文，避免模型补写用户未说出的经历 |
| `StageGenerator` | 分阶段生成开场、人物发言、讨论、追问和卡片 | 一次只解决一个阶段，失败时局部重试 |
| `PioneerProfile / PioneerMind` | 人物能力、价值、推理动作、语气、互动方式和来源 | 人物差异来自思维方式，不只是古风口吻 |
| `SourceRetriever` | 轻量 curated retrieval | 为发言与历史回声提供可追溯依据，MVP 不急于上向量库 |
| `LanguageEditor` | 事实边界、中文语法、自然度和衔接修订 | 只改善表达，不新增判断 |
| `OutputGuard` | 安全、重复、来源、行动具体性和事实边界检查 | 将高风险问题做成确定性约束或 repair 信号 |
| `PersistenceAdapter` | 会话、消息和卡片持久化 | 为历史记录与恢复预留统一接口 |

### 3.4 技术栈

- Next.js 15、React 19、TypeScript。
- OpenAI Chat Completions 兼容协议，可接入不同模型服务。
- JSON Schema / 字段校验、repair retry、阶段级 fallback。
- Supabase 作为可选持久化方案。
- `html-to-image` 导出行动卡和组合卡。

### 3.5 已有评测事实

- v0.5 固定题集覆盖副业、关系、家庭、自我价值、表达、未知原因情绪、已命名情绪和用户纠错等场景。
- 独立裁判从读题、人物区分、推进、重复、贴题、语言、安全、行动卡、金句卡九个维度评分。
- 历史一次基线在火山 GLM-5.2 下平均约 85，MVP 通过 4/8。
- 后续切换到智谱官网 GLM-5.2 后，同一旧代码重跑曾得到平均约 86、通过 7/8，说明裁判端点与单次波动足以改变结论。
- 曾观察到单题在近似条件下 89 → 73 → 88 的波动，因此项目不再用单次小幅分差证明改进。
- 当前采用确定性检查、LLM 粗门槛、人工体验三轨评测；最新未提交迭代仍需要完成同题人工回归，不能声称最终质量已经稳定。

## 4. 高频项目问题与参考回答

### Q1：为什么要做这个项目？

**回答结构：现象 → 用户缺口 → 产品假设 → 验证方式。**

我观察到两类产品都不够理想：普通 AI 往往给一个单一答案，名人模拟器又容易只模仿口吻，缺少真实的思想差异。我提出的产品假设是：如果让多个有明确价值系统和知识依据的女性视角分阶段参与，用户会更容易看见问题中的不同判断条件；如果最后再把谈话收成行动卡，体验就不只停留在“被安慰”。所以 MVP 不是先做大量人物，而是先验证提问、选人、圆桌、追问和行动收成这条闭环。

### Q2：为什么要做多角色圆桌，而不是直接让一个模型给三个观点？

直接生成三个观点更便宜，但用户看到的仍是一篇报告，缺少时序、回应和参与感。圆桌的价值来自三点：第一，不同人物有稳定的注意力和判断标准；第二，后发言者要基于已经说过的内容新增价值；第三，用户可以追问某一位，改变后续路径。因此我把角色差异、对话状态和调度关系都建模了。与此同时，我不认为角色越多越好，MVP 默认三位，就是为了控制延迟、成本和认知负担。

### Q3：这个项目真正的产品创新是什么？

不是“让名人聊天”本身，而是把角色扮演、反思对话和行动收成组合成可控的 AI 工作流。具体有三个创新点：

1. 人物差异不只写在语气里，而是拆为能力、知识、推理动作、互动边界和来源。
2. Director 不强制制造冲突，而是根据本场真实内容选择递进、互补、澄清或交锋。
3. 对话结果不是总结报告，而是可溯源到本场消息的行动卡与赠言卡。

### Q4：你为什么不只做 Prompt Engineering？

单 Prompt 很难同时稳定满足读题、选人、人物差异、历史承接、事实边界和卡片生成。任何一个要求变复杂，其他要求就容易丢失。因此我把系统拆成多个阶段，并把不同问题放在适合的层处理：状态和路由交给 Director，表达交给模型，来源交给 Retriever，确定性风险交给 Guard，失败交给 repair 和 fallback。Prompt 仍然重要，但它是 Harness 中的一层，不是整个产品。

### Q5：你怎么理解 Harness Engineering？

我把 Harness 理解为“围绕模型建立的一整套运行环境和控制系统”。模型负责概率性生成，Harness 负责输入如何组织、任务如何拆解、工具或知识如何调用、输出如何验证、状态如何推进、失败如何重试和降级、质量如何被观测。这个项目里，Director、ContextBuilder、StageGenerator、Retriever、Guard、Persistence 和 Evaluation 共同构成 Harness。它的目标不是消除模型随机性，而是让随机性处在可理解、可监控、可恢复的边界内。

### Q6：Roundtable Director 做了什么？为什么不能让模型自由决定？

Director 主要处理三类决策：读题和意图分类、人物与第一轮任务分配、讨论及追问调度。如果完全交给一次模型调用，系统容易强制交锋、选错回应者，或者把用户一句“我明白了”误判为继续分析。Director 将这些决策结构化为阶段、关系和 speech act，再让生成模型只完成当前发言。这样不仅更可控，也更容易在失败后定位究竟是读题、调度还是文案生成的问题。

### Q7：如何避免九位人物说成同一个人？

早期我只写了 `speakingStyle`，结果人物只是换语气说同一套建议。后来把人物拆成四层：

1. 能力层：擅长处理什么意图，输出什么价值。
2. 推理层：先看什么、如何区分、什么证据会改变判断。
3. 互动层：何时赞同、挑战、补充或让步。
4. 声音层：语气、节奏、提问方式、修辞额度和禁用模式。

评测上还计划使用“遮住姓名猜人物”的盲测。因为如果只能靠头像和标签辨认角色，人物系统其实没有立住。

### Q8：为什么使用 curated retrieval，而不是直接上向量 RAG？

第一版只有九位人物，每人少量高质量资料，语料规模不大，而且产品最重要的是来源准确和使用边界。此时用人工主题标签、中文分词和读题结果做可解释混合评分，成本更低，也更容易检查为什么召回。向量库会增加切分、embedding、索引、召回评测和运维复杂度，但不一定提升 MVP 质量。等人物和资料规模扩大、关键词召回明显不足时，再用 hybrid retrieval 会更合理。

### Q9：如何避免模型虚构名言或人物经历？

我不允许模型凭记忆现场生成历史名言。Historical Echo 来自人工核验的资料库，保存原文、中文自译、作品位置、来源 URL 和主题标签；系统只负责匹配，高度不相关时宁可不展示。人物发言可以做解释性角色扮演，但产品明确不声称真人一定会这样说，也不能虚构她经历过与用户相同的事情。事实正确性适合硬约束，文学性和自然度则留给模型和人工评测。

### Q10：模型输出不符合格式怎么办？

每个阶段要求结构化 JSON，先做 schema 和字段校验。如果字段缺失、来源错误或出现高风险问题，会发起聚焦 repair，而不是重跑整场对话。如果 repair 仍失败，才进入该阶段的本地 fallback。API 路由也按阶段拆分，因此一次请求失败只影响当前阶段，不需要清空 session。这里的原则是：尽量保留真实模型输出，只有明确的状态、安全或事实问题才硬降级。

### Q11：你如何设计 fallback？

最初所有人物共享通用 fallback，结果不同人物会说出相同的话，甚至第一轮和追问逐字重复。后来我认识到 fallback 也属于产品体验，不能只是技术兜底。因此 fallback 需要同时看当前 QuestionIntent、最新对话缺口和人物专属思维动作；生成后还要重新做贴题与跨阶段去重。高风险失败可以保守降级，但普通的风格问题不应该轻易把真实生成替换成僵硬模板。

### Q12：你如何选择生成模型与裁判模型？

我把两者分开。生成模型看中文表达、角色区分、结构化输出稳定性、延迟和成本；裁判模型需要独立配置，避免和生成模型完全同源。项目通过 OpenAI 兼容接口抽象模型供应商，方便切换。但切换裁判后不能直接比较历史分数，因为端点、权重和 Prompt 都可能改变量尺。正确做法是固定评测元数据，并用新裁判重新评价旧 baseline，再比较 before / after。

### Q13：项目里的 baseline 是什么？

Baseline 不是“平均 85 分”这一个数字，而是一套可复现版本包，包括代码提交、问题集、生成模型和参数、裁判模型、评测 Prompt、阈值、运行日期和典型失败输出。项目早期把单次分数当 baseline，后来发现生成和裁判都有方差。下一步更可靠的做法是冻结 golden transcripts，先固定生成内容，再让同一裁判重复评分，从而分离生成方差、裁判方差和 Harness 改动效果。

### Q14：你如何评测一个开放式 Agent 产品？

我使用三轨：

1. **确定性检查**：状态是否合法、来源是否存在、是否逐字重复、是否介绍全部人物、失败是否只重试当前阶段。这一轨证明具体 Bug 确实修复。
2. **LLM 评测**：评价读题、人物差异、贴题、推进、自然度、行动卡质量等语义维度，主要作为整体退化哨兵。
3. **人工体验**：判断句子是否自然、角色有没有活人感、互动是否有趣、操作是否清楚。

此外把数据分为 dev、regression、hidden 和 OOD，避免反复优化固定题集导致评测过拟合。

### Q15：为什么你不相信单次 LLM-as-a-Judge 分数？

因为我实测同一场景在近似条件下出现过 89、73、88 的波动，而裁判端点迁移后，同一旧代码的通过数也明显变化。这说明小幅分差可能小于测量噪声。我的处理不是弃用 LLM 裁判，而是改变它的职责：用确定性断言验证机械修复，用 LLM 裁判发现大范围退化和典型失败，用多次运行的中位数、方差和硬失败率评价稳定性。

### Q16：举一个你通过评测定位系统根因的例子。

一次关系边界场景从 89 分跌到 73 分，我先看到的是奥斯汀在第一轮和追问中逐字重复。最初怀疑是 Prompt 去重不足，但加入临时诊断日志后发现，真实输出被一个过严的 Guard 判为硬失败，两轮都掉进了同一个确定性 fallback。修复时我把该指标从硬失败降为软 repair，并增加 follow-up fallback 的二次去重。这个案例让我意识到：AI 产品出现坏文案时，根因可能不在模型，而在编排、校验或降级策略。

### Q17：你遇到过评测反过来伤害产品吗？

遇到过。为了让人物更短、更有区分，我曾不断增加固定开头、字数限制和角色动作，评测题可能更容易过，但真实用户问“如何提升表达能力”时，系统却把方法题硬塞进情绪分析，人物说话也越来越模板化。根因是把人物区分、自然度等软指标错误地实现成硬规则。后来我增加 QuestionIntent，把任务意图和情绪信息量拆开；同时只对事实、安全、状态做硬约束，把自然度和角色特色留给软 repair、盲测与人工体验。

### Q18：如何处理用户说“我明白了”或纠正模型？

我把 follow-up 意图细分为 question、reflection、commitment、correction、closure 等。用户纠正模型时，系统要撤回具体误读、记录 denied assumptions，再回到用户原意，而不是把纠正当成反驳；用户表达 closure 时，角色不应再写一段新分析，而由主持人简短确认并提供“生成行动卡 / 继续聊”。这类状态问题适合显式建模，不能只靠 Prompt 猜。

### Q19：你如何做成本与延迟控制？

目前的策略包括：默认只选三位角色；分阶段调用但每阶段只带必要上下文；Retriever 每人只返回少量来源；repair 聚焦错误字段；失败只重试当前阶段；卡片生成复用现有消息；低风险能力可以使用更便宜模型。尚未完成的部分是线上 token 预算、缓存、并发和 P95 延迟监控。如果进入真实上线，我会先记录各阶段 token、成功率、fallback 率和延迟，再决定哪些阶段降模型、缓存或合并调用。

### Q20：这个项目目前最大的不足是什么？

第一，它还没有真实规模用户数据，主要依靠固定题集和我的人工体验。第二，九位人物的资料深度不一致，目前只选择三位做了更完整的 PioneerMind 样板。第三，模型和裁判都有方差，质量稳定性还没有达到可重复的高质量标准。第四，历史记录、线上限流和可观测性还不完整。我不会把它包装成成熟产品，但它已经是一个可以完整运行、暴露失败并持续迭代的 MVP。

## 5. 与研发平台 / 开发者服务相关的问题

### Q21：你的项目是面向普通用户的，为什么适合研发平台岗位？

场景不同，但底层问题高度相似。Coding Agent 也需要理解任务、读取上下文、选择工具、分阶段执行、检查输出、处理中断、保存状态和评测成功率。我在圆桌项目中处理的是角色与对话任务，研发平台处理的是代码库、工具和开发任务；二者都需要 Harness、可观测性、权限边界和评测。我的短板是还没有大规模内部研发场景经验，所以入职后我会优先做开发者访谈和工作流观察，而不是直接把消费产品经验套过去。

### Q22：如果让你设计一个公司内部 AI Agent 平台，你会怎么开始？

我不会先做一个“万能 Agent”。第一步会选高频、可验证、风险可控的研发任务，例如日志解释、测试生成、代码库问答或 PR 信息整理。然后：

1. 访谈不同角色，记录任务频率、当前耗时、输入来源、完成标准和失败代价。
2. 选择一个端到端最短闭环，明确 Agent 能做和不能做什么。
3. 建立模型、工具、知识、权限、状态、评测和观测的通用底座。
4. 用任务成功率、人工接管率、修改接受率、节省时间和复用率评估，而不是只看调用量。
5. 从真实失败中抽象平台能力，避免为单一业务堆特判。

### Q23：研发平台产品和普通 AI 应用最大的差异是什么？

研发平台更强调可验证性、权限、安全、可观测性和集成成本。普通用户可能接受一段“有帮助”的回答，但开发者任务往往有明确产物：代码是否编译、测试是否通过、变更是否越权、引用是否准确。因此研发平台需要更多确定性反馈，例如编译器、测试、静态分析和仓库状态；同时必须支持人工确认、回滚、审计和最小权限。产品经理要把模型能力和工程约束一起设计。

### Q24：你会如何评测 Coding Agent？

我会沿用三轨但替换指标：

1. 确定性：构建、测试、lint、类型检查、改动范围、权限和状态一致性。
2. 语义质量：需求理解、方案合理性、代码可维护性、解释清晰度，由盲审或 LLM 裁判辅助。
3. 真实任务：开发者是否接受变更、人工修改量、首次成功率、完成时间、接管率和回退率。

题集也要分 dev、regression、hidden、OOD，并按仓库规模、语言、任务类型和风险分层。不能只用公开 benchmark，也不能让评测题泄漏进 Agent Prompt。

### Q25：开发者不信任 AI 生成代码，你会怎么办？

先拆解“不信任”的来源：可能是不了解改了什么、失败不可恢复、验证成本太高，或权限边界不清。对应产品方案包括：先展示计划和影响范围；生成 diff 而非直接覆盖；自动运行测试并展示证据；标出不确定点；对高风险操作要求确认；保留回滚和审计。信任不是靠一句免责声明建立的，而是靠可见过程、可验证结果和可控权限建立的。

### Q26：如何判断某个研发需求值得做成平台能力？

我会看五个维度：频率、耗时、标准化程度、失败风险和跨团队复用性。高频、输入输出相对清楚、可以自动验证、多个团队重复建设的需求更适合平台化。只服务一个团队且高度依赖隐性业务知识的需求，可以先做解决方案验证，等出现稳定共性后再下沉到底座。平台产品不能为了“通用”过早抽象，也不能长期堆业务特判。

### Q27：如何在模型能力、成本和体验之间做取舍？

先按阶段拆任务，不是全链路只选一个模型。需求理解、复杂规划可能需要强模型；格式转换、摘要、分类可以用更便宜模型；编译和测试则用确定性工具。对每阶段记录质量、延迟、token 和失败率，建立可替换的模型接口。产品目标不是使用最强模型，而是在关键用户指标和风险约束下找到最优组合。

### Q28：如何与技术团队判断一个 LLM 需求是否可行？

我会先把模糊需求改写成输入、输出、工具、上下文、完成标准和失败代价，然后与技术团队逐项验证：模型是否能获得必要上下文，是否存在确定性验证，延迟与成本是否可接受，权限和数据是否允许，失败能否降级。先用小样本 PoC 验证能力边界，再决定做产品、做辅助能力还是暂不做。这样产品讨论不会停留在“模型看起来很聪明”。

### Q29：你如何看待 Agent 平台里的模型、工具和知识？

模型负责理解与生成，工具负责执行确定性动作，知识负责提供组织上下文，Harness 负责把三者在正确的状态和权限下组织起来。平台价值不只在于接入更多模型，而在于让业务团队可以复用工具协议、权限、记忆、观测、评测和降级能力，并知道一次失败发生在哪一层。

### Q30：如果上线后 Agent 的成功率没有提升，你怎么排查？

我会先按链路拆分指标：任务进入、意图分类、上下文召回、工具调用、模型输出、验证、人工确认和最终完成。然后检查失败集中在哪类任务、哪个阶段、哪个模型或哪个工具。还要区分离线成功率与线上接受率：离线通过但用户不采用，可能是可解释性、交互成本或信任问题；线上完成但成本过高，则是路由和上下文问题。最后用失败聚类决定是修 Prompt、工具、知识、交互还是产品范围。

## 6. 产品判断与执行问题

### Q31：你如何确定 MVP 范围？

我用“是否能验证核心价值”来决定。这个项目的核心不是九位人物、登录或支付，而是用户能否经历一场多视角对话并留下可执行结果。所以 MVP 优先完成提问、选人、顺序对话、追问、行动卡。历史记录、完整知识库、付费和大规模 RAG 都后置。这样可以先验证最不确定的体验，而不是先建设昂贵基础设施。

### Q32：你如何做优先级？

我会综合用户影响、发生频率、风险、依赖和验证成本。比如“用户纠正后系统仍坚持误读”会直接损害信任，属于 P0；人物语言不够有趣影响体验，是 P1；历史记录很重要，但不影响首次闭环，可以是 P2。对于 AI 产品，我还会额外看问题位于生成层还是系统层，优先修复会跨场景复现的系统根因。

### Q33：举一个你没有采纳的方案。

我曾考虑直接上向量 RAG，也考虑让所有人物强制发生交锋。前者在九位人物、少量 curated 资料阶段增加了系统复杂度，却没有明确召回收益；后者能增加表面热闹，但经常制造与用户问题无关的假冲突。最后我选择可解释的轻量检索，以及由 Director 按真实观点判断是否递进、互补或交锋。

### Q34：如果只有两周，你会如何推进这个项目？

第一周锁定核心场景和评测基线，完成问题理解、单轮多角色、追问和行动卡闭环；同时埋点各阶段成功率、延迟和 fallback。第二周用小规模真实用户测试，集中修复 P0 信任问题，例如误读、重复、来源错误和无法恢复，再完成部署与作品集材料。我不会在两周内扩展九位完整知识库或支付系统。

### Q35：你如何协调设计和研发？

这个项目主要由我独立完成，所以我不会虚构正式跨部门管理经验。但我在多 Agent 协作中有意识地使用产品文档、状态机、接口字段、验收标准和失败样本来减少歧义。真实团队中，我会把产品承诺、技术约束和体验标准放在同一份可执行规格里；对开放式质量，用例子和评测定义对齐，而不是只写“更自然、更智能”。

### Q36：AI Coding 给你带来了什么，也有什么风险？

它显著提高了探索、实现和审查速度，让我可以同时覆盖产品、前端和 Harness。但风险也很明显：Agent 会重复读取大文件、在上下文压缩后丢失约束、为了通过测试增加局部补丁，甚至建议破坏性 Git 操作。因此我会维护 handoff 文档、限制改动边界、先查看 git diff、禁止重置他人改动，并用类型检查、构建、Harness 断言和人工体验验收。AI Coding 提高的是产出速度，不替代产品判断和代码责任。

## 7. 行为面问题

### Q37：讲一次你犯错并修正的经历。

**Situation**：为了提高固定评测题的通过率，我不断增加人物固定开头、字数和动作要求。  
**Task**：我需要让多角色回答更稳定、更有区分。  
**Action**：真实体验后发现系统把方法问题误判为情绪问题，语言也越来越模板化。我回到根因，把 QuestionIntent 与 SupportMode 分开，区分硬约束和软质量指标，并重新设计 dev、regression、hidden、OOD 题集。  
**Result**：我没有用一个更高的单次分数证明成功，而是建立了更可靠的迭代机制。这件事让我理解，评测应该帮助发现问题，不能反过来统治生成。

### Q38：讲一次你解决复杂问题的经历。

可以使用“89 → 73 → 88 的重复 fallback”案例。重点不是分数，而是：先记录现象；提出多个假设；加日志确认 Guard 硬失败；定位到 fallback；将不适合的硬门槛降为 soft repair；增加二次去重；用确定性断言验证。

### Q39：讲一次你做取舍的经历。

可以使用“不上大型向量 RAG”案例。说明用户价值、数据规模、工程成本和可验证性，结论是先用 curated retrieval，保留未来升级路径。

### Q40：你最大的优势是什么？

我的优势是能把模糊的 AI 体验问题拆成产品结构和可验证机制。我既关注用户觉得内容是否自然、有价值，也愿意深入到状态、上下文、fallback 和评测方差，定位问题究竟发生在哪一层。我不是只提需求，也会用 AI Coding 把假设做成可运行 MVP，再根据失败修正判断。

### Q41：你目前的短板是什么？

我缺少大规模内部研发平台和正式跨团队项目经验，目前项目的用户样本也有限。我的补足方式是：不把个人项目经验过度包装；主动阅读研发工具与 Agent 论文；用真实代码、评测和失败记录训练技术判断；进入团队后优先理解内部开发流程、指标和组织约束。

### Q42：为什么想来字节跳动开发者服务团队？

我希望做的不只是一个使用模型的功能，而是让不同业务团队都能更可靠地使用模型。开发者服务团队覆盖需求分析、编码、测试、发布和运维全生命周期，最吸引我的地方是它既需要理解模型，也需要理解工程系统和开发者体验。我的个人项目让我对 Harness、评测、失败恢复和 Agent 可控性产生了很强兴趣，我希望把这些方法放到更真实、更大规模的研发场景中继续打磨。

## 8. 面试官可能继续追问的技术细节

### 8.1 为什么分阶段 API，而不是一个长连接完成全部？

- 用户可以看到进度，并在中间调整人物或追问。
- 单阶段失败可重试，避免重新消耗整场 token。
- 每阶段上下文和 schema 更清楚，便于监控与定位。
- 代价是调用次数和延迟增加，后续可用流式输出、并发准备和模型分级优化。

### 8.2 为什么结构化 JSON 仍然需要应用层校验？

- 模型可能返回合法 JSON，但字段语义不合法。
- schema 不能证明人物来源正确、内容未重复或行动可执行。
- 因此需要 schema、业务校验、语义 Guard 和人工评测分层负责。

### 8.3 为什么不是所有问题都硬拦截？

- 安全、状态、来源和事实边界适合硬约束。
- 自然度、人物特色、文学性具有主观性，硬拦截容易把模型推入僵硬 fallback。
- 对软问题优先 repair、打标和评测，不轻易丢弃真实输出。

### 8.4 多 Agent 和多角色是什么关系？

项目更准确地说是“一个 Director 编排多个角色生成任务”，不是多个自主 Agent 各自拥有长期规划和工具执行。面试时不要夸大为完整多 Agent 系统。它具备 Agentic Workflow 的状态、角色、路由和评测，但自治程度有限，这是为了 MVP 的可控性。

### 8.5 Supabase 做到什么程度？

代码中已有 PersistenceAdapter 和会话、消息、卡片接口，环境变量可选；但登录、完整历史记录、恢复和收藏仍属于后续产品事项。不要说已经有成熟用户历史系统。

## 9. Case：如果现场让你设计 AI Coding 产品

### 题目：为公司内部开发者设计一个 AI 需求到代码 Agent

#### 1. 先定义用户和场景

- 新业务开发者：不了解代码库与规范。
- 熟悉业务的开发者：希望减少重复实现、测试和排障时间。
- Reviewer / Tech Lead：关心改动质量、风险和可审计性。

优先选择“已有代码库中的小型、可测试需求”，暂不承诺跨仓库大型重构。

#### 2. 核心流程

```text
需求输入
→ 需求澄清与验收条件
→ 代码库检索与影响分析
→ 生成计划
→ 用户确认
→ 分步骤改码
→ 自动测试 / lint / 类型检查
→ 展示 diff、证据和风险
→ 人工接受、修改或回滚
→ 失败进入评测与回归集
```

#### 3. 平台能力

- 模型路由与上下文管理。
- 代码检索、工具协议和权限。
- 任务状态、checkpoint、重试与恢复。
- 沙箱、审计和最小权限。
- 构建、测试和静态分析集成。
- Trace、token、延迟、失败分类与评测平台。

#### 4. 核心指标

- 端到端任务成功率。
- 首次构建 / 测试通过率。
- 开发者接受率和人工修改比例。
- 完成时间与节省时间。
- 人工接管率、回滚率、越权率。
- 单任务成本和 P95 延迟。
- 7 日 / 30 日开发者复用率。

#### 5. 风险

- 需求误解导致“正确实现错误问题”。
- 上下文召回不足或过量。
- 修改范围失控。
- 测试通过但业务语义错误。
- 权限、隐私和依赖供应链风险。

#### 6. MVP 验证

选择 2–3 个仓库、两类重复任务，小范围灰度。先证明开发者愿意采用且验证成本下降，再扩任务类型。评测同时保留离线 benchmark、隐藏回归题和真实开发者接受数据。

## 11. 面试中不要夸大的内容

- 不说“有大量用户”，目前主要是人工体验和离线评测。
- 不说“完成了完整 RAG”，当前是 curated lightweight retrieval。
- 不说“稳定提升了 X 分”，裁判方差较大，当前更可靠的是结构性修复证据。
- 不说“完整多 Agent 自治系统”，更准确是可控多角色 Agentic Workflow。
- 不说“已完成登录和历史记录”，代码有持久化接口，但产品能力尚未完整验收。
- 不说“独立带领研发、设计、运营团队”，可以说独立覆盖这些职能并形成协作规格。

## 12. 面试前最后速记

### 一句话项目价值

我把一个容易做成 Prompt Demo 的多角色聊天，重构成了有状态、可检索、可校验、可降级、可评测的 Agent 产品 MVP。

2. 能建立评测、观测、回归和失败归因闭环。
3. 能用 AI Coding 快速实现，同时保持范围、证据和技术边界意识。

### 三个最值得讲的失败

1. 固定题集与硬规则造成评测过拟合。
2. Guard 过严导致真实输出被替换成重复 fallback。
3. 裁判模型迁移和随机性让单次分数失去可比性。
